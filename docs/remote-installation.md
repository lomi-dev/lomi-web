# Remote installation endpoints

The website generates these static entry points during every Astro build:

```sh
curl -fsSL https://lomi.dev/remote/install.sh | sh
```

```powershell
powershell -ExecutionPolicy Bypass -c "irm https://lomi.dev/remote/install.ps1 | iex"
```

They select Linux, macOS, or Windows and x86_64 or ARM64, download a pinned
release asset, and verify its exact size and SHA-256 before executing any
downloaded code. The machine does not need Rust, Node.js, or a compiler.
Linux continues through the release's Ed25519-authenticated preflight and TUF
updater. macOS and Windows execute the signed installer from the verified ZIP;
its existing native-signature and TUF checks still apply. Windows never runs
the bundled signed script through `Invoke-Expression`: it needs a real file
path for its self-signature verification.

The first-stage script is trusted through HTTPS and the website deployment.
Its embedded pins protect against replacement of assets at the release origin;
they cannot protect against replacement of the website's script itself. The
existing independently reviewed Linux `install-command.txt` remains available
for installations requiring that separate pinning channel.

The scripts print the existing installer's next setup command. Device login,
service setup, and workspace sharing are completed there, with explicit user
choices. The scripts do not run the interactive wizard through pipeline stdin.
They leave shell profiles and PATH unchanged.

## Platform requirements

- Linux: a supported GNU/glibc release, POSIX shell, curl, OpenSSL 3,
  sha256sum, unzip, and GNU core utilities. musl/Alpine and 32-bit targets do
  not have release bundles.
- macOS: curl, shasum, ditto, codesign, and sudo (provided by macOS). An
  administrator password may be requested through the terminal. The default
  account is the invoking user, or `SUDO_USER` when already elevated. A root
  session without `SUDO_USER` must select `LOMI_REMOTE_ACCOUNT` explicitly.
  `LOMI_REMOTE_HOST_MODE` selects `manual`, `login`, or `boot` (default).
- Windows: Windows PowerShell 5.1 or PowerShell 7, a trusted Authenticode
  certificate chain, and TLS 1.2 support. The bootstrap detects the native OS
  architecture, including from an emulated shell.

For example, install macOS for the current account in manual mode:

```sh
curl -fsSL https://lomi.dev/remote/install.sh | LOMI_REMOTE_HOST_MODE=manual sh
```

## Enabling a release

Without release inputs, both endpoints deliberately fail with an unavailable
message and exit unsuccessfully. A malformed or partially configured input
fails the website build. No endpoint resolves a mutable `latest` URL or takes
executable commands from the CMS.

1. Build and sign all six Host bundles using `lomi-remote/release/build_release.py`.
   Complete the existing release-set qualification and TUF metadata signing.
2. Generate the canonical installation catalog using
   `lomi-remote/release/build_installation_catalog.py`, following its
   [release guide](../../lomi-remote/release/README.md#installation-page-input).
   It verifies the approved release-set declarations, all bundle and Linux
   sidecar bytes, and the public root. Review its exact output and SHA-256.
3. Publish every referenced asset at its exact HTTPS URL. Download requests
   deliberately reject redirects; GitHub download URLs that redirect require
   an origin serving the bytes directly.
4. Set the following public **build arguments** in Coolify for `Dockerfile.site`:
   `LOMI_REMOTE_INSTALLATION_CATALOG_JSON` (the exact compact JSON, without a
   trailing newline) and `LOMI_REMOTE_INSTALLATION_CATALOG_SHA256` (the
   independently reviewed lowercase digest). Rebuild the website.

For local builds, export the same values before running `bun run build`:

```sh
export LOMI_REMOTE_INSTALLATION_CATALOG_JSON="$(cat /reviewed/installation-catalog.json)"
export LOMI_REMOTE_INSTALLATION_CATALOG_SHA256=REVIEWED_SHA256
bun run build
```

These values contain public metadata only. Never put signing keys or
credentials in the catalog, site environment, or Docker build arguments.
Updating the catalog and rebuilding the site publishes the next pinned release.
The public launch page's content is managed separately from these endpoints.

Nginx serves both files as `text/plain` with `Cache-Control: no-store` and
`X-Content-Type-Options: nosniff`. Equivalent `_headers` rules are included for
static hosting. Apply a matching cache bypass if an upstream proxy has a
custom rule that overrides origin cache headers. Astro development middleware
serves the same generated bytes locally.

## Options and verification

Download the script to inspect it or supply existing installer options:

```sh
curl -fsSL https://lomi.dev/remote/install.sh -o /tmp/lomi-remote-install.sh
sh /tmp/lomi-remote-install.sh --help
sh /tmp/lomi-remote-install.sh --version 0.1.0 --no-path
```

The version above is illustrative. `--version VERSION` requires the version
embedded in that particular site build; it never switches to unreviewed assets.
Other installer options, including `--install-dir`, are forwarded to the
bundled installer. macOS retains its fixed protected installation directory.
On macOS an initial `uninstall` selects administrator uninstall for the chosen
account and mode. On Linux and Windows, uninstall follows the existing bundled
installer's behavior. Existing profiles must satisfy its maintenance checks.

Run `bun run test:remote-installers` for catalog and bootstrap regression tests,
then `bun run build` with the project's supported Node.js version. Inspect
`dist/remote/install.sh` and `dist/remote/install.ps1`. After deployment, verify
HTTP 200, plain-text content types, and no-store headers for both URLs before
testing a real installation on each release platform.
